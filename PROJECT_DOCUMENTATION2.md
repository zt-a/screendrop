# 1. Общее описание проекта

## 1.1. Название

ScreenDrop — локальная система беспроводной передачи файлов между смартфонами, компьютерами и Android-экранами.

## 1.2. Назначение

ScreenDrop предназначен для упрощения обмена файлами в университетских аудиториях, учебных центрах, конференц-залах и других помещениях с интерактивными Android-экранами.

Приложение позволяет отправлять документы непосредственно на большой экран без использования мессенджеров, облачных хранилищ, USB-накопителей и сторонних серверов.

Основной способ организации сети — использование мобильной точки доступа Wi-Fi (Personal Hotspot) одного из студентов.

## 1.3. Проблема

В учебных аудиториях часто возникает необходимость передать презентацию или другой документ на компьютер либо Android-экран преподавателя.

Традиционные способы имеют недостатки:

- Передача через WhatsApp требует открытия веб-версии или авторизации.
- Telegram требует подключения к интернету.
- USB-накопитель необходимо физически подключать к устройству.
- Облачные хранилища требуют подключения к интернету.
- Отправка файлов преподавателю через личные мессенджеры создаёт дополнительную нагрузку.
- Передача большого количества файлов затрудняет организацию учебного процесса.

## 1.4. Предлагаемое решение

ScreenDrop превращает Android-экран в локальный приёмник файлов.

Студент включает Hotspot на своём смартфоне. Преподаватель подключает Android-экран к этой точке доступа. ScreenDrop запускает локальный сервер и отображает QR-код.

Студент сканирует QR-код, выбирает документ в браузере и отправляет его на экран.

После успешной передачи файл сохраняется в локальном хранилище Android-устройства.

## 1.5. Основные преимущества

1. Работа без интернета.
2. Отсутствие облачной инфраструктуры.
3. Передача файлов по локальной сети.
4. Подключение через QR-код.
5. Отсутствие обязательной установки приложения на телефоны и компьютеры.
6. Поддержка нескольких отправителей.
7. Контроль полученных файлов преподавателем.
8. Локальное хранение документов.

# 2. Цели и задачи проекта

## 2.1. Главная цель

Разработать автономную систему локального обмена файлами, использующую сетевые возможности операционной системы Android.

## 2.2. Задачи

- Разработать Android TV-приложение.
- Реализовать встроенный HTTP-сервер.
- Реализовать обнаружение сетевых интерфейсов.
- Реализовать работу через Personal Hotspot.
- Реализовать QR-подключение.
- Разработать мобильный веб-интерфейс.
- Реализовать потоковую передачу файлов.
- Реализовать управление принятыми файлами.
- Добавить проверку целостности файлов.
- Реализовать контроль доступа к сессиям.
- Подготовить автоматические тесты.
- Подготовить техническую документацию.

## 2.3. Измеримые результаты

Проект считается реализованным на уровне MVP, если:

- Android APK устанавливается на совместимый экран.
- Приложение запускает локальный сервер.
- Телефон подключается к сети Hotspot.
- QR-код открывает страницу передачи.
- PDF успешно передаётся.
- Файл сохраняется на Android TV.
- SHA-256 полученного файла совпадает с исходным.
- Преподаватель может открыть или удалить файл.
- Основной сценарий работает без интернета.

# 4. Архитектура системы

## 4.1. Общая архитектура

ScreenDrop реализуется по клиент-серверной модели.

Android TV выступает сервером, а смартфоны и компьютеры — клиентами.

Основные компоненты:

1. Android Application.
2. Network Manager.
3. HTTP Server.
4. Session Manager.
5. File Transfer Engine.
6. File Storage.
7. Web Sender.

## 4.2. Архитектурная схема

```text
             STUDENT SMARTPHONE
             ==================

             Wi-Fi Hotspot
                   |
             Mobile Browser
                   |
             QR Code Scanner
                   |
                   |
              Wi-Fi Network
                   |
                   |
             ANDROID TV
             ==========

          +-------------------+
          |   ScreenDrop UI   |
          +-------------------+
                   |
          +-------------------+
          |   Network Manager |
          +-------------------+
                   |
          +-------------------+
          |   Ktor HTTP Server|
          +-------------------+
                   |
          +-------------------+
          |  Session Manager  |
          +-------------------+
                   |
          +-------------------+
          | File Transfer     |
          | Engine            |
          +-------------------+
                   |
          +-------------------+
          |   File Storage    |
          +-------------------+
```

## 4.3. Основной сетевой сценарий

1. Телефон студента включает Wi-Fi Hotspot.
2. Преподаватель подключает Android TV к Hotspot.
3. Android TV получает локальный IP-адрес.
4. Network Manager определяет активный сетевой интерфейс.
5. Ktor запускает HTTP-сервер.
6. Session Manager создаёт временную сессию.
7. QR Generator создаёт QR-код с адресом сервера и токеном.
8. Студент сканирует QR-код.
9. Браузер отправляет HTTP-запрос на Android TV.
10. File Transfer Engine принимает файл.
11. File Storage сохраняет документ.
12. SHA-256 подтверждает целостность.
13. UI отображает новый документ.

## 4.4. Важное ограничение Personal Hotspot

Наличие соединения Android TV с точкой доступа ещё не гарантирует возможность обращения к телевизору со смартфона, который создал эту точку доступа.

Реализация Hotspot и маршрутизации зависит от версии Android и производителя устройства.

Поэтому необходимо проверять фактическую доступность HTTP-сервера.

Основной MVP использует прямое соединение:

```text
Smartphone Browser
       |
       | HTTP Request
       |
       v
Android TV HTTP Server
       |
       v
File Storage
```

Если телефон не может обратиться к телевизору, приложение должно показать диагностическое сообщение.

Необходимо документировать, на каких моделях устройств режим проверен.

Возможное будущее расширение — Phone Transfer Hub, при котором телефон выступает сервером, а телевизор инициирует получение файлов.

Данный механизм не входит в обязательный MVP.

# 7. Нефункциональные требования

## 7.1. Производительность

- Сервер не должен блокировать UI thread.
- Передача должна использовать потоковую запись.
- Количество параллельных загрузок должно быть ограничено.
- Интерфейс должен обновляться асинхронно.
- Потребление RAM должно оставаться разумным для Android TV.
- Большие файлы не должны целиком загружаться в оперативную память.

## 7.2. Надёжность

- Ошибка одного клиента не должна останавливать сервер.
- Потеря Wi-Fi должна корректно обрабатываться.
- Незавершённые загрузки должны оставаться недоступными как готовые файлы.
- Сервер должен корректно освобождать сокеты.
- Повторный запуск не должен создавать второй экземпляр сервера.

## 7.3. Совместимость

Целевые платформы:
- Android TV.
- Android Smart Display.
- Android Smartphone Browser.
- Desktop Browser.

Минимальную версию Android необходимо определить после проверки реальных университетских экранов.

## 7.4. Локальность

- Передача файлов не должна зависеть от внешнего интернета.
- Файлы не должны отправляться на сторонние серверы.
- QR-код должен содержать локальный адрес.
- Данные должны храниться локально на Android TV.

## 7.5. UX

- Интерфейс телевизора должен поддерживать D-pad.
- Текст должен быть читаемым с расстояния.
- Главная функция должна быть доступна с одного экрана.
- Ошибки должны отображаться понятным языком.

# 9. Network Specification

## 9.1. Network Modes

В первой версии поддерживаются два сценария.

### Mode A — Personal Hotspot

Основной режим.

1. Студент включает Hotspot.
2. Android TV подключается к нему.
3. Android TV получает сетевые параметры.
4. ScreenDrop запускает сервер.
5. Студент открывает QR-ссылку.
6. Выполняется передача.

### Mode B — Existing Wi-Fi

Дополнительный режим.

Оба устройства подключены к одной Wi-Fi сети.

Приложение проверяет возможность прямого соединения.

## 9.2. Network Discovery

Network Manager должен получать:

- Active Network.
- Network Capabilities.
- Link Properties.
- IPv4 Address.
- Interface Information.

Необходимо учитывать:
- Несколько сетевых интерфейсов.
- VPN.
- Ethernet.
- Wi-Fi.
- Изменение маршрутов.
- Ограничения доступа между клиентами.

Нельзя безусловно выбирать первый обнаруженный IPv4-адрес.

## 9.3. Server Binding

HTTP Server должен слушать подходящий адрес.

Для LAN-сценария используется:

```text
0.0.0.0
```

Однако приложение должно проверять, что сервер действительно доступен через нужный интерфейс.

Порт должен быть конфигурируемым.

Начальное значение:

```text
8080
```

## 9.4. Network Health Check

Перед отображением QR-кода приложение должно проверить:

1. Есть ли активное сетевое соединение?
2. Есть ли IPv4?
3. Запущен ли сервер?
4. Доступен ли выбранный интерфейс?
5. Нет ли ошибки bind?
6. Можно ли продолжить работу?

Важно: локальная проверка на самом телевизоре не доказывает, что телефон может подключиться к нему. Реальную связность нужно проверять с клиентского устройства.

# 10. HTTP API Specification

Base URL:

```text
http://TV_IP:8080
```

Все API-запросы выполняются в локальной сети.

## 10.1. GET /

Возвращает Web Sender.

Response:

```http
HTTP/1.1 200 OK
Content-Type: text/html
```

## 10.2. GET /api/health

Проверка состояния сервера.

Response:

```json
{
  "status": "ready",
  "server": "ScreenDrop",
  "version": "1.0.0"
}
```

## 10.3. GET /api/session

Получение текущей сессии.

Требуется действительный токен.

Response:

```json
{
  "active": true,
  "expiresAt": "2026-11-11T18:00:00Z",
  "maxFileSize": 104857600
}
```

## 10.4. POST /api/upload

Передача файлов.

Headers:

```http
Authorization: Bearer SESSION_TOKEN
Content-Type: multipart/form-data
```

Multipart fields:

```text
file
senderName
```

Response:

```json
{
  "success": true,
  "file": {
    "id": "random-file-id",
    "name": "presentation.pdf",
    "size": 2048000,
    "sha256": "..."
  }
}
```

## 10.5. GET /api/files

Получение списка принятых файлов.

Требуется авторизация.

Response:

```json
{
  "files": [
    {
      "id": "file-id",
      "name": "presentation.pdf",
      "size": 2048000,
      "mimeType": "application/pdf",
      "receivedAt": "2026-11-11T17:30:00Z"
    }
  ]
}
```

## 10.6. DELETE /api/files/{id}

Удаление файла.

Требуется авторизация.

Response:

```json
{
  "success": true
}
```

## 10.7. POST /api/session/close

Завершение текущей сессии.

Response:

```json
{
  "success": true,
  "status": "closed"
}
```

## 10.8. HTTP Error Codes

| Код | Значение |
|---|---|
| 200 | Успешный запрос |
| 201 | Файл создан |
| 400 | Неверный запрос |
| 401 | Отсутствует авторизация |
| 403 | Доступ запрещён |
| 404 | Ресурс не найден |
| 413 | Файл слишком большой |
| 415 | Неподдерживаемый формат |
| 429 | Превышен лимит запросов |
| 500 | Внутренняя ошибка |
| 503 | Сервер временно недоступен |

## 10.9. API Security

Все endpoints управления файлами и сессиями должны требовать авторизацию.

Публичным может быть только минимальный health endpoint и страница первичного подключения.

Токен не должен записываться в обычные логи.

# 11. File Transfer Specification

## 11.1. Поддерживаемые форматы

Документы:
- PDF.
- PPT.
- PPTX.
- DOC.
- DOCX.
- TXT.

Изображения:
- JPG.
- JPEG.
- PNG.

Видео:
- MP4.

## 11.2. Начальные ограничения

| Параметр | Значение |
|---|---|
| Максимальный размер файла | 100 MB |
| Одновременные загрузки | 3 |
| Максимальная длина имени | 255 символов |
| Срок сессии | 30 минут бездействия |
| Начальный HTTP-порт | 8080 |

Значения должны быть конфигурируемыми.

## 11.3. Алгоритм передачи

1. Клиент выбирает файл.
2. Проверяет предварительные ограничения.
3. Отправляет multipart-запрос.
4. Сервер проверяет токен.
5. Сервер проверяет лимиты.
6. Создаёт временный файл.
7. Начинает потоковое чтение.
8. Одновременно записывает данные и вычисляет SHA-256.
9. Проверяет завершение передачи.
10. Перемещает файл в постоянное хранилище.
11. Создаёт метаданные.
12. Уведомляет UI.

## 11.4. Потоковая запись

Запрещается без необходимости загружать весь файл в RAM.

Пример логики:

```text
HTTP Multipart Stream
        |
        v
Input Stream
        |
        +----> SHA-256 Digest
        |
        v
Temporary File
        |
        v
Integrity Check
        |
        v
Final Storage
```

## 11.5. Collision Handling

Если файл с таким именем уже существует:

- Не перезаписывать предыдущий.
- Генерировать уникальное внутреннее имя.
- Сохранять оригинальное имя в metadata.

## 11.6. Storage

Использовать приватный каталог приложения.

Например:

```text
files/
  received/
    <file-id>/
      content
      metadata.json

  temporary/
    <upload-id>.part
```

Временные файлы должны удаляться при неуспешной передаче.

# 12. Session Management Specification

## 12.1. Создание сессии

При запуске приёма файлов создаётся новая сессия.

Поля:

- Session ID.
- Token.
- Created At.
- Expires At.
- Last Activity.
- Status.

## 12.2. Token Generation

Использовать криптографически стойкий генератор случайных чисел.

Минимальная энтропия токена — 128 бит, рекомендуется 256 бит.

Токен не должен зависеть от IP, времени или порядкового номера.

## 12.3. Session Lifecycle

```text
CREATED
   |
   v
ACTIVE
   |
   +------> EXPIRED
   |
   +------> CLOSED
```

## 12.4. QR Payload

QR-код содержит:

```text
http://TV_IP:8080/?token=SESSION_TOKEN
```

Web Sender должен использовать токен для авторизации запросов.

После завершения сессии старый токен должен перестать работать.

QR-код необходимо обновлять при смене сессии и сетевого адреса.

# 13. Security Specification

## 13.1. Основные угрозы

- Несанкционированная загрузка.
- Перехват сетевого трафика.
- Path Traversal.
- Подмена имени файла.
- Переполнение хранилища.
- Чрезмерное количество соединений.
- Повреждение файлов.
- Использование старого QR-кода.

## 13.2. Защитные механизмы

- Случайные session tokens.
- Срок действия токенов.
- Проверка авторизации.
- Ограничение размера.
- Ограничение числа загрузок.
- Filename sanitization.
- Проверка MIME.
- Проверка расширений.
- SHA-256.
- Приватное хранилище.
- Безопасная работа с временными файлами.

## 13.3. HTTP Limitations

В MVP допускается HTTP в пределах локальной сети.

Однако HTTP не шифрует передаваемые данные.

Поэтому:
- Не отправлять конфиденциальные документы в недоверенных сетях.
- Не считать токен заменой TLS.
- Не логировать токены.
- Не оставлять сессию открытой после занятия.

В будущем рекомендуется HTTPS с корректной моделью доверия для локальных устройств.

Временные токены, ограничения доступа, валидация и изолированное хранилище.

# 22. Ограничения проекта

На момент разработки MVP известны следующие ограничения:

1. Совместимость зависит от конкретных Android TV и смартфонов.
2. Hotspot может ограничивать доступ между устройствами.
3. HTTP не шифрует содержимое файлов.
4. Для открытия документов нужны подходящие приложения.
5. Некоторые Android TV могут ограничивать фоновые процессы.
6. Отдельные функции могут требовать системных разрешений.
7. Приложение не гарантирует работу через университетскую сеть с Client Isolation.

Эти ограничения должны быть отражены в итоговой документации, а не скрыты.
